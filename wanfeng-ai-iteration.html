一句话结论：先不要做量化。第一阶段只证明一件事 —— 系统能改自己：Chat 里说一句话，它自己在 Gitea 开出一个 PR，人只做合并。

量化的门禁、DAG 分解、多智能体评审全部只留接口不实现。判断第一阶段成功的标准只有一条：循环能不能转起来。接口留得对不对，决定第二部分能不能不动架构地接上去。

定位澄清：第一部分建成的是一个可靠的自动化层，不是"会自我进化的系统"。系统的能力上限由底层模型决定，循环次数不改变这一点；什么算"更好"由人定义，结果由人负责。详见第三部分。

五、留口径 · 四个扩展点

本阶段最重要的产出。功能可以后补，但接口现在不定义好，后面就要动大手术。量化的 quant-gate、多智能体评审，未来都插在这些点上。

1门禁协议 Gate

未来加 quant-gate 只需一行注册，不用改调度器。

# gate/base.py
from typing import Protocol, Any
from dataclasses import dataclass

@dataclass
class GateResult:
    passed: bool
    hard_fail: bool          # True = 直接淘汰，不参与后续打分
    score: float | None      # 0~1，软性评分；hard_fail 时为 None
    evidence: dict[str, Any] # 证据，必须可追溯
    message: str

class Gate(Protocol):
    name: str
    def run(self, ctx: "RunContext") -> GateResult: ...

# 注册表 —— 未来加 quant-gate 只需一行
GATES: list[Gate] = []
def register(gate: Gate) -> None: GATES.append(gate)

2适应度 Fitness

现在不用，但循环调度器调用它的位置要留出来。

class Fitness(Protocol):
    def score(self, ctx: "RunContext") -> dict[str, float]: ...

# 第一阶段： 返回 {"tests_passed": 1.0} 即可
# 未来：    {"oos_sharpe": ..., "max_drawdown": ..., "turnover": ...}

3触发器 Trigger

class Trigger(Protocol):
    def should_run(self) -> str | None: ...   # 返回需求描述，None = 不触发

# 第一阶段：ManualTrigger（只有人提交才跑）
# 未来：    CronTrigger（定时）、EventTrigger（策略衰减信号）

七、验收标准

唯一硬标准：在 Chat 里输入一句需求，系统自动在 Gitea 开出一个 PR，中间无需人工干预。

三条底线

检查标准
可追溯每个工单的每一步都有日志和工件，能回答"它当时为什么这么改"
失败可控跑不通会停，不会无限重试，不会留下半成品分支
边界安全Agent 无法写出 worktree 之外、无法推主干、无法合并 PR

八、明确不做的事

写下来是为了防止范围蔓延。

量化门禁 quant-gate（只留 Gate 接口） DAG 分解 / 多工单编排（一次只跑一个） 多智能体并行评审（单 Agent） 人机决策门白名单（全部人工） 自动合并（永不在本阶段） 容器隔离（worktree 够用） PostgreSQL 迁移（SQLite 够用） 模型微调 权限系统 / 多用户

九、风险

风险表现对策
Agent 改坏代码提了个把项目搞崩的 PR人合并 + 分支隔离 + 测试门禁；主干永远安全

Gitea token 泄露写进代码或日志token 只走环境变量；日志脱敏
半成品分支堆积失败后分支没清理失败即删分支，或打 failed 标签保留供排查

一、三件必须先拍板的事

这三项会决定后面所有设计，建议在服务器到位前就有结论，避免返工。

!代码权威源：GitHub 与 Gitea 互斥

项目管理/github/EIGHT_ARMS_WORKFLOW.md 明确写着：「GitHub 是源码、Issue、Milestone、PR、commit、tag、验收状态和发布状态的唯一权威源」，而八爪鱼「仅可单向投影，不得反向改写 GitHub，也不得成为第二权威源」。本方案要求「代码和文档用 Gitea」，与这条治理铁律直接冲突 —— 必须二选一，或者重写这条治理。

选项含义评价
AGitea 升为唯一权威，GitHub 降为只读镜像 —— 治理模型不变（仍是"单一权威源 + 只读投影"），只换权威源。现有 Issue 按 wanfeng-issue-id 幂等迁移，一次性成本，之后自洽推荐
BGitHub 保留权威，Gitea 只做 agent 运行面 —— 治理零改动，但 Gitea 沦为纯展示层，与"代码用 Gitea"的初衷不符次选
C双权威并行 —— 两边都写必然漂移，你的治理文档已经预判了这个失败模式不可取

!部署基线：Windows → Linux

回测平台当前基线是 Windows + Python 3.12 + PostgreSQL strict + DeepSeek + loopback 监听（127.0.0.1:8020），快速开始文档通篇是 PowerShell。服务器是 Linux，且要对外提供 Web 访问 —— 这两处都要改：进程管理、路径、启动脚本，以及从 loopback 改为受控的外部监听（必须加认证与 TLS，不能裸奔）。

!Chat 入口的权限定位

这决定整个系统的风险上限。建议沿用八爪鱼的人机决策门分法，并结合已有的 agent_approvals.py：

  • 执行类可自动 —— 跑回测、写代码、开分支、跑测试、生成评审报告，可以白名单自动放行。
  • 业务决策永远人工 —— 合并主干、发布、动生产库、改策略上线参数、删除持久资源。这条不给任何白名单覆盖。量化系统涉及真金白银，建议比八爪鱼更严：连"策略进入实盘候选池"都设为人工门。

四、核心难点：量化的"验收"和软件不一样

这是整个蓝图里最需要想清楚的部分 —— 八爪鱼没有现成答案，直接照搬会出事。

普通软件的自迭代（八爪鱼的模型）量化系统的自迭代（真实风险所在）
验收 = 跑测试，绿灯即通过验收 = 回测，但回测绿灯 ≠ 策略有效
"通过"是确定性的、可复现的过拟合、前视偏差、幸存者偏差
迭代越快 → 质量越高迭代越快 → 过拟合越快
评审看代码逻辑评审必须看样本外与统计显著性
最大风险：自迭代系统会极大地加速策略搜索。在量化里，搜索得越快，过拟合来得越猛 —— 系统会很勤奋地为你找到一堆"历史上很美、未来会亏钱"的策略。因此 quant-gate 不是可选项，而是这套系统的安全阀，它的严格程度决定了系统是资产还是负债。

quant-gate 建议的检查项

检查做法不通过
样本外验证严格 IS/OOS 时间切分，OOS 是唯一准入依据，IS 表现仅供参考拒绝
多重检验校正Deflated Sharpe / PBO —— 记录本轮搜索了多少个变体并据此折算显著性拒绝
前视审计每个特征的数据时间戳必须早于决策时间戳，自动扫描拒绝
滚动稳健性滚动窗口重测，参数邻域扰动不塌陷降级
成本敏感性滑点/费率 ×2 情景下仍成立降级
容量约束给出策略可承载的资金规模上限降级
上线后衰减监控滚动 IC / 回撤 / 换手漂移，退化超阈值即触发再迭代触发迭代

P23–5 周量化门禁 quant-gateIS/OOS 切分、多重检验校正、前视审计、成本与容量敏感性、上线后衰减监控。这是投入产出比最高、也最不能省的一环。验收：构造一个明显过拟合的策略，系统能拦下它并给出具体证据（而非笼统拒绝）
P3持续自迭代闭环 + 人机决策门变异算子、适应度函数、事件触发、审批流接入 Chat、工件两层体系、DAG 分解与多工单编排。验收：某策略衰减后系统自动生成并验证一版改进，人工在 Chat 里看证据后一键合并
一个建议：P2 的 quant-gate 建议提前到 P1 并行做。理由是：如果先跑通了自动迭代却没有门禁，系统会在你还没建立起信任的时候，先给你产出一批不可信的策略 —— 那比没有系统更糟。先有刹车，再装引擎。

六、完整形态的风险

风险说明对策
过拟合加速系统越自动，搜到的假策略越多quant-gate 是安全阀，不得为速度放松
成本失控迭代循环放大 token 消耗，DeepSeek 单供应商预算闸 + 多供应商降级链 + 高频低价值环节用小模型
自动合并越界一旦给实盘自动权，错误会被自动放大业务决策永远人工；实盘上线永不自动
数据写入事故agent 误写生产库继承现有 source_writes=0 只读契约，执行沙箱化
外网暴露当前是 loopback，对外开放后攻击面扩大必须 TLS + 强认证；管理面与业务面分离
治理双源GitHub/Gitea 状态漂移见本节决策 A：单一权威源，另一侧只读
第三部分 · 边界与责任

自我改进的边界：定义权与责任都在人

这一节界定系统不做什么，以及为什么。它决定了第一部分该被定位成"可靠的自动化层"，而不是"会进化的系统"。

一、能不能实现代码自迭代"进化"

能，但"进化"这个词必须先拆开 —— 拆开后会看到，一半是今天就能做的工程，另一半目前不存在。

最关键的一点：吞吐 ≠ 能力。循环跑起来后，系统能做的是把"模型本来就会做的小改动"自动做完 —— 修 bug、补测试、升依赖、清告警，一天做一百件。但它不会因此比底层的 DeepSeek 更聪明。跑一万轮循环，不会跑出一个模型自己想不到的架构。
会累积的不会累积的
脚手架 —— 测试套件、文档、工具、提示词、历史修复库。这些确实复利增长，系统"整体"确实在变强 能力 —— 遇到模型不懂的难题，循环一万次还是不懂

准确的说法是：harness 会进化，模型不会。而 harness 进化的天花板，就是模型的能力。

二、卡点在"选择"，不在"变异"

进化需要三件事：变异、选择、遗传。变异（Agent 改代码）和遗传（PR 合并、下轮基于新代码）都好办。卡死在"选择"上。

软件没有适应度函数。这是根本困难，不是实现细节。
候选适应度为什么不行
单元测试只能否决，不能排序。测试通过 = 没搞坏，不等于变好了。它是约束，不是目标。没有梯度，搜索就没有方向
圈复杂度 / 覆盖率 / 行数全部可刷。任何一个拿来当目标，系统都会学会用最省事的方式刷它 —— 删代码、写空断言、堆无意义测试
"用户想要的"需要人的判断，不可自动化

这就是 Goodhart 定律在代码上的形态：当一个指标变成目标，它就不再是好指标。

三、对比量化 —— 正好相反

代码自迭代量化自迭代
适应度太弱（测试只能否决）太强（夏普是个数）
结果无方向漂移疯狂过拟合
危险蠢，但安全聪明，但亏钱

这个对比很说明问题：量化的适应度函数异常好用，也异常危险 —— 正因为它是个干净的数值，搜索会全力利用它，包括利用它的漏洞。quant-gate 存在的全部理由就是这个。

所以从"能否自我进化"看，量化反而比通用代码更合适 —— 前提是刹车装好。

四、按野心分四层

层级内容适应度成立？
L0人给目标，系统做完开 PR测试今天就能做 可靠。这是第一部分，是自动化，不是进化
L1系统读自己的日志 / 报错 / 失败测试，自己提炼工单能否复现并修掉真实故障真能跑 而且有用
L2窄而可测的目标让它磨：覆盖率、类型错误、lint、依赖新鲜度、性能基准客观、难刷谦虚但诚实 能持续累积真实价值
L3系统自己定义"更好"—今天做不到 谁声称做到了，是在卖东西

五、必须防的失败模式：腐化累积

长期跑下去最真实的威胁 —— 不是"AI 造反"，而是没人看得懂的代码库。

每一次改动都通过了测试。五百次之后，代码局部自洽、全局混乱。没有一次改动是错的，但整体已经不是任何人设计的东西了。

建议写进门禁的对策

  • 架构不变式由门禁强制 —— 模块依赖边界、新增依赖需人工批准
  • 变更预算 —— 限制单位时间改动速率，不让它一口气重写
  • 每轮都有回滚点
  • 定期人工审计累积改动，不只是审单个 PR
  • 回归测试必须随迭代增长 —— 它同时是安全网和适应度来源

六、人来定义，人为结果负责

这是整套系统的基本原则，优先于前面所有技术设计。 系统的自动化程度可以提高，但定义权和责任都不能转移给系统。

1定义权在人：什么算"更好"，由人定义

系统不能自己推断目标。第一阶段"更好"的定义就是人写下的验收标准；量化的"更好"是人选定的适应度函数与硬约束。系统可以提出候选目标，但采纳与否由人决定。这条堵死的正是 L3。

2责任在人：结果是人的结果，不是系统的结果

"系统自动做的"不是免责理由。策略亏了钱，是批准上线的人的责任；代码腐化了，是批准合并的人的责任。自动化改变的是执行方式，不改变责任的归属。

3因此每一层自动化都要有具名负责人

不是"团队负责"，是每一条自动化流水线、每一个门禁阈值、每一次策略上线，都要有一个具名的人对该层结果负责。没有具名负责人的自动化，不应被启用。

4这不是"人在环上"，是"人在两端"

人在两端：入口定义目标与约束，出口承担结果与责任。中间的执行过程可以完全自动。
这不同于"每个动作都要人确认" —— 那会让系统瘫痪，等于没建。
人挪到两端，不是被去掉。

决策类型谁定例子
执行系统自动跑测试、写代码、开分支、跑回测、生成评审报告
目标与阈值人定义，系统执行验收标准、适应度函数、门禁阈值、变更预算
结果与责任永远是人合并主干、策略上线、预算分配、资源删除
底线：能不能自我进化，最终取决于谁来当裁判。有可信裁判（测试、基准、回测）→ 在它能测量的范围内，能。没有可信裁判 → 只能靠人。这不是实现问题，是逻辑问题：你无法让系统验证它自己无法验证的东西。

七、对本方案的结论

内容结论理由
第一部分（L0）建自动化的价值是真实的。但定位应为可靠的自动化层，不是"会进化的系统"
L1 / L2建有边界、有真实收益、适应度客观
L3不建它会很勤奋地给你产出一堆没人看得懂的代码
量化 + quant-gate真正的目标那里有唯一一个干净可用的适应度函数，代价是必须配一个足够严的 quant-gate
